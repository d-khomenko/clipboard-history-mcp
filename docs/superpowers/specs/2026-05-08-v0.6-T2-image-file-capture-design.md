# T2 — Image + file capture sub-spec

**Status:** Draft
**Date:** 2026-05-08
**Author:** Dmytro Khomenko + Claude
**Topic:** Daemon captures pasteboard images and file URLs in addition to text. Blobs land on disk under `data_dir/blobs/`; MCP tools return metadata + opt-in base64 payload; vault-mirror writes the blob alongside the existing sidecar.

---

## 1. What this track adds (scoped narrowly)

- **Pasteboard reader** returns a `Clip` enum with three variants instead of a `String`:
  - `Clip::Text(String)` — current behaviour, unchanged. macOS + Linux.
  - `Clip::Image { bytes, mime }` — **macOS only in v0.6**. PNG or TIFF via `objc2-app-kit` (the dep added for T1). Linux deferred — `arboard::get_image` returns raw RGBA which requires a PNG encoder; adding one is cheap (`png = "0.17"`) but pushes scope; v0.7 picks it up when a Linux user actually asks.
  - `Clip::Files(Vec<PathBuf>)` — **macOS only**. `NSFilenamesPboardType`. Linux deferred (arboard does not expose paths cleanly).
- **Schema v2** adds four nullable columns on `clips` describing the payload, plus a content-hash index for blob dedup. Migration uses the existing `if current < N` ladder in `core/db.rs::open_db`, no separate runner.
- **Blob storage** under `data_dir/blobs/<aa>/<sha256>.<ext>` (git-style two-char loose-object sharding). Same SHA-256 = same blob = `copy_count` bump on the existing row, no duplicate file.
- **MCP surface** extends three tools and adds zero new ones:
  - `list_history` and `get_item` include `payload_kind`, `mime_type`, `blob_size_bytes`. `get_item` adds an opt-in `with_blob: bool = false` parameter; when `true`, returns a base64 data URL.
  - `restore_clip` writes the blob back to the pasteboard with the correct UTI on macOS / MIME on Linux. Refuses files whose underlying path no longer exists with a clear error.
  - `delete_item` deletes the blob file from disk along with the row (best-effort; logs a warn if blob missing).
- **Vault-mirror** writes the blob alongside the sidecar at `<vault>/clipboard/YYYY-MM/<id>-<kind>-<slug>.<ext>` and references it from the sidecar markdown body via standard `![alt](path)` syntax.
- **Capture limits**: env var `CLIPBOARD_MAX_BLOB_BYTES`, default `26214400` (25 MB). Values larger than the limit are skipped with a `WARN`-level log line that names the size and the source app.

## 3. Concrete file-by-file changes

### 3.1 Schema migration (`src/core/db.rs`)

Add a new `SCHEMA_V2` constant and extend the existing migration ladder:

```rust
const SCHEMA_V2: &str = r#"
ALTER TABLE clips ADD COLUMN payload_kind TEXT NOT NULL DEFAULT 'text';
  -- 'text' | 'image' | 'file'
ALTER TABLE clips ADD COLUMN blob_path TEXT;
  -- relative path under data_dir/blobs/, NULL for text
ALTER TABLE clips ADD COLUMN blob_size_bytes INTEGER;
  -- NULL for text
ALTER TABLE clips ADD COLUMN mime_type TEXT;
  -- 'image/png', 'image/tiff', 'application/octet-stream', etc. NULL for text
CREATE INDEX IF NOT EXISTS idx_clips_payload_kind ON clips(payload_kind);
UPDATE meta SET value = '2' WHERE key = 'schema_version';
"#;
```

Extend `open_db`:

```rust
if current < 1 { conn.execute_batch(SCHEMA_V1)?; }
if current < 2 { conn.execute_batch(SCHEMA_V2)?; }
```

T2 does not add image/file content to the FTS index; search remains text-first. A future track may add filename / EXIF / OCR indexing.

### 3.2 Pasteboard reader (`src/core/pasteboard.rs`)

Replace `pub fn read_clipboard() -> Result<String>` with:

```rust
pub enum Clip {
    Empty,
    Text(String),
    Image { bytes: Vec<u8>, mime: &'static str },
    Files(Vec<PathBuf>),
}

pub fn read_clip() -> Result<Clip>;
```

Implementation order inside `read_clip`:

1. Check `is_transient()` (T1) — return `Clip::Empty` if true.
2. macOS: query `NSPasteboard.types()` priority order:
   1. `public.png` → return `Clip::Image { bytes, mime: "image/png" }`
   2. `public.tiff` → return `Clip::Image { bytes, mime: "image/tiff" }` (do NOT transcode)
   3. `NSFilenamesPboardType` → parse plist array of paths, return `Clip::Files(...)`
   4. `public.utf8-plain-text` / `NSStringPboardType` → return `Clip::Text`
   5. else → `Clip::Empty`
3. Linux: query `arboard` priority order:
   1. `clipboard.get_text()` → return `Clip::Text`
   2. image / files: not supported on Linux in v0.6 — return `Clip::Empty`. Image support deferred per §1.
4. The existing `read_clipboard()` text-only API stays for compatibility; rewrite it as a thin wrapper:

```rust
pub fn read_clipboard() -> Result<String> {
    match read_clip()? {
        Clip::Text(s) => Ok(s),
        _ => Ok(String::new()),
    }
}
```

So existing call sites that only care about text continue to work unchanged.

`write_clipboard` (used by `restore_clip`) gains a sibling:

```rust
pub fn write_clip(clip: &Clip) -> Result<()>;
```

For `Clip::Image` and `Clip::Files` it sets the appropriate UTI on macOS and the appropriate target on Linux (image only).

### 3.3 Watcher tick (`src/daemon/watcher.rs`)

Replace the existing `tick`'s text-only branching with:

```rust
let clip = pasteboard::read_clip()?;
match clip {
    Clip::Empty => return Ok(()),
    Clip::Text(text) => {
        // Existing text-tick path, unchanged.
        // (Last-seen dedup, transient/ignore-app checks, secret detection, etc.)
    }
    Clip::Image { bytes, mime } => store_blob_clip(...)?,
    Clip::Files(paths) => store_files_clip(...)?,
}
```

Two new private helpers `store_blob_clip` and `store_files_clip` live in `watcher.rs` and:

1. Hash the blob with SHA-256.
2. Look up `clips` by hash. If a row exists → bump `copy_count`, update `last_copied_at`, mirror to vault if not already. Return.
3. Otherwise: enforce `CLIPBOARD_MAX_BLOB_BYTES`. If over → log warn + drop.
4. Write blob to `data_dir/blobs/<aa>/<sha256>.<ext>` atomically (tmp + fsync + rename, mirroring `core::vault::atomic_write`).
5. Insert a new `clips` row with `payload_kind`, `blob_path`, `blob_size_bytes`, `mime_type`.
6. Vault-mirror per §3.7.

For `Clip::Files(paths)`, each path is treated as a separate blob — copy the file content into `blobs/`, hash it, dedup. Symlinks resolved before copy. Files larger than the limit are dropped per-file (others in the same `Files(...)` may still capture).

### 3.4 Pasteboard classifier (`src/core/types.rs`)

Add a `payload_kind_for(clip: &Clip) -> PayloadKind` helper returning the variant defined in §3.5. The existing `classify(text)` is unchanged — it operates on text only and is called only from the `Clip::Text` arm.

### 3.5 Store API (`src/core/store.rs`)

Extend `ClipInput` with payload fields and add a new constructor:

```rust
pub struct ClipInput {
    pub text: Option<String>,
    pub primary_kind: String,
    pub kinds: Vec<String>,
    pub source_app: Option<String>,
    pub window_title: Option<String>,
    // New (all None for text clips, set for image/file):
    pub payload_kind: PayloadKind,
    pub blob_path: Option<PathBuf>,
    pub blob_size_bytes: Option<i64>,
    pub mime_type: Option<String>,
}

pub enum PayloadKind { Text, Image, File }
```

`add_clip` writes the new columns. `find_by_hash` (existing) takes precedence: if hash matches, bump `copy_count` instead of inserting.

`get_item` returns the new fields. The `text` column stays `Option<String>` and remains the source of truth for text clips; image/file clips have `text = NULL`.

`delete` deletes the blob file from disk after the row is removed (best-effort, log warn if the blob is missing — could happen if user manually nuked the data dir).

### 3.6 MCP tools (`src/mcp/tools.rs`)

Three of the existing 15 tools change. No new tools.

`list_history` response — extend each item with:

```json
{
  "id": 42,
  "preview": "...",
  "primary_kind": "image",
  "payload_kind": "image",
  "mime_type": "image/png",
  "blob_size_bytes": 482000,
  "source_app": "Preview",
  "captured": "2026-05-08T12:34:56Z"
}
```

`get_item` adds a `with_blob: Option<bool>` parameter (default `false`). When `true` AND `payload_kind != "text"`, the response includes a `blob_data_url` field set to `data:<mime>;base64,<payload>`. When `false`, only the metadata is returned (consistent with current default behaviour for text clips). Returning an entire base64 image is opt-in to keep MCP responses small — Claude can ask for it explicitly.

`copy_item` (the existing tool — name kept for backwards-compat) — dispatch on `payload_kind`:
- `"text"`: existing path (unchanged after T1's let-else refactor).
- `"image"`: read blob from `blob_path`, call `pasteboard::write_clip(&Clip::Image { ... })`.
- `"file"`: verify the file still exists at the resolved path; if yes, write `Clip::Files(vec![path])`; if no, return JSON `{"error": "file no longer exists at original path", "lastKnownPath": "..."}`.

Refusal of secret-text continues unchanged (image/file are never classified as secrets).

### 3.7 Vault mirror (`src/core/vault.rs`)

Extend the existing `mirror_clip` flow:

- Compute the slug from `primary_kind` and a short hash prefix (current behaviour for text).
- For image/file clips, copy the blob from `data_dir/blobs/<sha>` to `<vault>/clipboard/YYYY-MM/<id>-<kind>-<slug>.<ext>` using the same `atomic_write` helper. The destination filename uses the same id-and-slug pattern as the sidecar so they sit next to each other.
- The sidecar markdown body adds a single image-link line for `image` clips:

  ```markdown
  ![Captured image](<id>-<kind>-<slug>.<ext>)
  ```

  For `file` clips, the body lists them as link bullets:

  ```markdown
  - [`original-name.ext`](<id>-<kind>-<original-name>.ext) (filed locally — original at `/Users/.../somewhere`)
  ```

- Frontmatter gains two new keys:
  - `payload_kind: "image" | "file"`
  - `mime_type: "image/png"` (etc.)

- Daily-note line gains a 📎 marker and a wikilink to the sidecar (existing `[[id-kind-slug]]` link works unchanged).

Confirmation on Obsidian rendering: standard `![]()` markdown image syntax with a relative path resolves correctly inside vault-relative folders, even when the surrounding markdown has YAML frontmatter. No Obsidian config required.

### 3.8 CLI (`src/cli/install.rs` + plist/unit emitter)

Plumb `CLIPBOARD_MAX_BLOB_BYTES` through the same env-var-on-the-service-spec path that `CLIPBOARD_VAULT_PATH` uses. No new CLI flag needed — installer already serialises any `CLIPBOARD_*` env var that's set in the parent process. Document the variable.

### 3.9 Cargo.toml

New top-level dep:

```toml

```

Used by `mcp::tools::get_item` to encode the blob bytes when `with_blob: true`. Tiny dep, no transitive bloat.

`image` crate is **not** added — we store the pasteboard's native PNG/TIFF bytes verbatim. Consumers (Obsidian, Preview.app, browsers) all handle PNG/TIFF natively.

## 5. Explicitly NOT in this track

- **Animated GIF / video.** Stored as opaque blobs (`mime_type: "image/gif"` / `"video/quicktime"`), no thumbnail or preview generation.
- **Image transcoding.** TIFF stays TIFF; PNG stays PNG. No `image` crate dependency.
- **OCR.** Image text is not extracted into `clips.text` or FTS. Future track if user signal warrants.
- **Linux file capture.** `arboard` does not expose file paths cleanly; deferred until a target-specific crate (or a Wayland portal) lands.
- **Linux image capture.** Punted to v0.7 along with adding a `png` encoder dep (`png = "0.17"`) for arboard's RGBA. macOS-only image in v0.6 keeps the dep set tight.
- **Windows.** Same v0.7 story as the rest of the roadmap.
- **Blob encryption at rest.** The `secrets` table stays the only encrypted store; blobs land plaintext on disk. Rationale: most images are not secrets, the encryption tax is significant (10–50 MB AES-GCM per capture), and the daemon's filesystem is already inside the user's home directory which is the natural trust boundary. Revisit in v0.7 if a "treat-as-secret blob" feature is added.
- **Thumbnail generation for vault sidecars.** Obsidian renders the full image inline; a separate thumbnail file isn't needed.
- **Image preview in `list_history`.** `with_blob: true` is `get_item`-only; `list_history` returns metadata only to keep batch responses tractable.
- **Per-app blob policies.** `CLIPBOARD_IGNORE_APPS` already covers "skip this app entirely"; no per-app blob-size policy.
- **Re-organising the existing schema migration scaffold into a numbered-patch framework.** The roadmap §5 lists this as v0.7. T2 just extends the existing `if current < N` ladder.

## 6. Definition of done

T2 ships when **all** are true:

1. `pbcopy < small.png && claude "show last image"` returns the image (verified manually on macOS).
2. Repeating the same image once does NOT duplicate the row — `copy_count` increments instead. Verified by `add_image_clip_and_dedup_on_repeat` test.
3. `delete_item(N)` removes both the row and the blob file from disk. Verified by `delete_image_clip_removes_blob` test.
4. Schema migration runs cleanly on a v1 database with rows present; existing text rows survive with `payload_kind = 'text'`. Verified by `migrates_v1_to_v2_preserves_existing_rows` test.
5. With `CLIPBOARD_VAULT_PATH` set, copying an image produces both the sidecar markdown AND the image file at the matching path. The sidecar body contains `![Captured image](relative-path.png)`. Verified by `image_clip_writes_blob_alongside_sidecar` and `image_sidecar_body_contains_relative_image_link` tests.
6. `cargo test` and `cargo clippy --all-targets -- -D warnings` are green on the merge commit.
7. README **Configuration** table documents `CLIPBOARD_MAX_BLOB_BYTES`. CHANGELOG `[Unreleased]` covers the Added/Changed bullets above.
8. `restore_clip` on an image clip restores the blob to the system pasteboard with the correct UTI on macOS. Verified manually.
9. `restore_clip` on a file clip whose source path was deleted returns the JSON error shape from §3.6 (`error` + `lastKnownPath`). Verified by a unit test against a temp file we delete before restore.

## 7. Open questions resolved (vs roadmap §8)

| Roadmap §8 question | Resolution |
|---|---|
| `CLIPBOARD_MAX_BLOB_BYTES` default | **25 MB** (`26214400`). 10 MB silently drops common Figma/screenshot exports; 50 MB is generous but bloats DB if a user pastes a 4K screenshot loop. 25 MB hits the median use-case and is overridable. |
| Vault image rendering in Obsidian | **Confirmed** — standard markdown `![alt](relative-path.png)` works inside vault-relative folders even when the markdown body has YAML frontmatter. No Obsidian config needed. Verified empirically against a fresh vault before drafting this spec. |

The other roadmap §8 questions belong to T3 (`pin_item` wiring), T4 (crate name on crates.io), and T5 (notarization) — not in scope here.

## 8. Sequencing within T2

T2 itself is a single coherent change but the implementation plan will sequence it as:

1. Schema migration (db.rs) — first, otherwise nothing else compiles cleanly.
2. `Clip` enum + `read_clip` / `write_clip` (pasteboard.rs) — enables capture.
3. Watcher dispatch (watcher.rs).
4. Store API extensions (store.rs).
5. MCP tool extensions (tools.rs).
6. Vault-mirror image path (vault.rs).
7. Tests added throughout.
8. README + CHANGELOG.

Each step is its own commit. Implementation plan (writing-plans) decomposes them into TDD tasks per the same pattern as T1.

## 9. Risk register

- **Data loss on schema-migration failure.** Mitigation: existing `if current < 2` block runs in a transaction implicitly via `execute_batch`; if any `ALTER TABLE` fails (extremely unlikely on SQLite), `meta.schema_version` stays at 1 and the next daemon start retries.
- **Disk fill from large blobs.** Mitigation: `CLIPBOARD_MAX_BLOB_BYTES` cap. Future work: configurable retention by total bytes, not just `CLIPBOARD_HISTORY_MAX` row count.
- **Sensitive screenshots silently archived.** Mitigation: `CLIPBOARD_NEVER_STORE_SECRETS=1` paranoid mode applies the same drop logic to image clips (fast path: skip ALL non-text capture in paranoid mode? Or only those that match heuristics?). Decision: in paranoid mode, drop all images and files entirely. Implementation: short-circuit in `watcher::tick` before hashing.
- **Vault-mirror file proliferation.** Mitigation: dedup on hash means repeating the same image does not write a new file. The vault stays as small as the source set.
- **Restore for files whose path moved.** Spec'd above — clear MCP error, no silent failure.
