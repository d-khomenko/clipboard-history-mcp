# clipboard-history-mcp — v0.6 adoption-first roadmap

**Status:** Draft
**Date:** 2026-05-08
**Author:** Dmytro Khomenko + Claude
**Topic:** Strategic roadmap for v0.6. Six independent tracks decomposed for sequential or parallel implementation. Each track will get its own sub-spec when picked up for `writing-plans`.

---

## 1. Why now

v0.5 closed the unique-tech story. clipboard-history-mcp is the **only OS-level history-capturing MCP server with security-grade handling** (gitleaks-class detection + AES-GCM at rest + Touch ID + FTS5 + Obsidian mirror, in a single ~24 MB Rust binary). Of ~30 `clipboard-mcp` repos on GitHub, the next-closest competitor is `vlad-ds/maccy-clipboard-mcp` (9★, reads Maccy's database — does not capture).

What v0.5 did **not** close:

- **Table-stakes vs native clipboard managers** (Maccy, Raycast, Paste, Pastebot, Alfred, CopyQ): no image / file capture, pinned/favorites only partially exposed, no `cargo install` distribution, no MCP-Registry listing. New users hit these gaps before they ever reach the unique features.
- **Quality nits visible on first read** of the codebase: a handful of `.expect()` / `.unwrap()` in production paths, a silently-broken `is_transient()` (always returns false since v0.4 — password-manager pastes can leak through the ignore-list), dead exports (`change_count`, `config_dir`), a stale "macOS clipboard history MCP" CLI about-string that contradicts shipped Linux support.
- **Discoverability mechanics**: not on `awesome-mcp-servers`, not on Glama, not in the official MCP Registry — three independent zero-effort to medium-effort steps each.

v0.6 converts unique tech into **adoptable product**. Heavy lifts (Windows port, persistent audit log + secret TTL, semantic search, cross-device sync, LLM-aware tools) explicitly defer to v0.7+ rather than dilute v0.6's adoption focus.

**Strategic framing:** v0.5 = "interesting niche thing." v0.6 = "product I'd actually install."

## 3. Tracks

Six tracks. Each is independent enough to PR separately. Sequencing in §4.

### T1 — Quality polish

**Scope.** Codebase audit quick-wins from the 2026-05-08 audit, scoped to "things visible on first read of `src/`":

- Replace `.expect("encrypt")` and `.expect("decrypt")` in `src/core/crypto.rs:31,101` with proper `Result` return paths. AES-GCM cannot legitimately fail given valid key+nonce length, but `expect` aborts the daemon process instead of bubbling an error.
- Replace `.unwrap()` patterns in `src/mcp/tools.rs:275, 359` and `src/core/vault.rs:192` with explicit pattern matches. The surrounding guards make them safe today; the patterns are brittle.
- Remove dead code: `change_count()` in `src/core/pasteboard.rs:36` (unused since v0.3), `config_dir()` in `src/core/paths.rs:20` (no consumers).
- **Fix `is_transient()` silent regression in `src/core/pasteboard.rs`** — currently always returns `false` since v0.4 cross-platform refactor. This is the primary mechanism for skipping password-manager copies on macOS; the `CLIPBOARD_IGNORE_APPS` env var was supposed to be a *secondary* defence. Without it, any pasteboard data marked `org.nspasteboard.ConcealedType` from an unknown app gets captured. Restore via `objc2-app-kit` raw NSPasteboard type query.
- Update `cli/mod.rs:11` clap `about` string from "macOS clipboard history MCP" to "Cross-platform clipboard history MCP" — Linux has shipped since v0.4.
- Update `src/core/biometry.rs:63-65` non-macOS / non-Linux fallback to log a prominent `tracing::warn!` rather than silently returning `Ok(true)`. (Even though no Windows build exists yet, this matters for code reading.)

**Out of scope for T1.** Performance fixes (regex re-compile in hot path, N+1 queries in `list_with`/`search`), schema migration framework, vault-write size cap. Those are medium-effort and belong in their own track or v0.7.

**Effort.** 1 day. ~10 small commits, all in `src/`. No schema, no MCP tool changes.

**Success.** Zero `.unwrap()` / `.expect()` reachable from `run_daemon` or `run_server` outside tests; `is_transient()` returns `true` for password-manager pasteboards on macOS (verified with 1Password / Bitwarden).

### T2 — Image + file capture

**Scope.** The single largest competitor gap. Every native clipboard manager (Maccy, Raycast, Paste, Pastebot, Alfred, CopyQ) supports image and file copies; `vlad-ds/maccy-clipboard-mcp` exposes them as base64. clipboard-history-mcp captures only `text` today.

**Data-model deltas.**

```sql
ALTER TABLE clips ADD COLUMN payload_kind TEXT NOT NULL DEFAULT 'text';
  -- 'text' | 'image' | 'file'
ALTER TABLE clips ADD COLUMN blob_path TEXT;
  -- relative path under data_dir/blobs/, NULL for text clips
ALTER TABLE clips ADD COLUMN blob_size_bytes INTEGER;
  -- NULL for text clips; populated for image/file
ALTER TABLE clips ADD COLUMN mime_type TEXT;
  -- 'image/png', 'image/jpeg', 'application/octet-stream', etc.
```

**Capture path (`src/daemon/watcher.rs` + `src/core/pasteboard.rs`).**

1. Extend `pasteboard::read_clipboard()` return type from `String` to `enum Clip { Text(String), Image(Vec<u8>, String /*mime*/), Files(Vec<PathBuf>) }`.
2. macOS: read `NSPasteboardTypePNG` / `NSPasteboardTypeTIFF` / `NSPasteboardTypeFileURL` via `objc2-app-kit`. Linux: `arboard::Clipboard::get_image()` already supports image; `arboard` does not expose file paths cleanly — file capture is **macOS-only in v0.6**, Linux gets a `tracing::debug!` skip.
3. Capture limits: env var `CLIPBOARD_MAX_BLOB_BYTES` (default 10 MB). Larger blobs are skipped with a `clip too large` log line.

**Storage path.**

- Blobs land in `data_dir/blobs/<aa>/<sha256>.<ext>` where `<aa>` is the first two hex characters of the hash (git-style loose-object sharding so directory listings stay flat as content grows). SHA-256 dedup: re-copying the same image just bumps `copy_count` on the existing clip row.
- `blob_path` stores the relative path so `data_dir` moves don't break the DB.
- Vault-mirror writes the blob alongside the sidecar: `<vault>/clipboard/YYYY-MM/<id>-image-<slug>.png` plus the existing `<id>-...-md` sidecar that frontmatter-references the image.

**MCP surface.**

- `list_history` and `get_item` return `payload_kind`, `mime_type`, `blob_size_bytes`. For image clips, optionally include a base64 data URL in `get_item` only when caller passes `with_blob: true` (default `false` — keeps responses small).
- `restore_clip` writes back to the pasteboard with the correct UTI on macOS / MIME on Linux. Refuses for `payload_kind = 'file'` if the underlying file no longer exists.
- `delete_item` also deletes the blob from disk (best-effort — log warn if blob missing).

**Effort.** ~1 week real-time. Largest track in v0.6. New tests: round-trip PNG, round-trip file URL on macOS, dedup-by-hash for repeat-paste, blob cleanup on `delete_item`.

**Success.** `pbcopy < small.png && claude "show last image"` returns the image. Repeating the same image once does not duplicate the row. Vault sidecar links the image file. Blob removed from disk on delete.

### T3 — Pinned / favorites finish

**Scope.** Schema column `clips.is_pinned INTEGER NOT NULL DEFAULT 0` already exists (verified in `src/core/db.rs` schema). MCP tool `pin_item(id, pinned: bool)` listed in v0.3 release notes. T3 verifies the wiring and closes gaps.

**What needs verification (audit before implementation, may be partly done).**

- `pin_item` is exposed and tested.
- `list_history(pinned_only: true)` returns only pinned items.
- Daemon's `MAX_ITEMS` ring-buffer prune (currently in `src/core/store.rs`) **excludes** pinned items. Today this may or may not hold — if not, pinning is a lie because pinned clips silently disappear.
- README documents the feature in the Tools (15) table.

**What's likely missing.**

- A `clear_history` exclusion path for pinned items (`clear_history(keep_pinned: bool = true)` default true).
- Vault-mirror `daily/` notes do not yet visually distinguish pinned items (low priority — possibly skip for v0.6).

**Effort.** ½ day if MCP tool already wired; up to 1 day if `pin_item` is missing or prune logic needs fixing.

**Success.** `pin_item(N)` followed by 1000+ new captures: clip N still listed by `list_history(pinned_only=true)`. Documented in README under "Tools (15)" or whichever section.

### T4 — `cargo install clipboard-history-mcp`

**Scope.** Publish to crates.io so Claude Code users can install with one command instead of cloning + `cargo build --release` + `claude mcp add ...`.

**Steps.**

1. Audit `Cargo.toml` for crates.io-required metadata: `description`, `license`, `keywords` (max 5), `categories`, `repository`, `documentation`, `readme`. Add what's missing.
2. Verify `Cargo.lock` is committed (it is).
3. Publish dry-run from local: `cargo publish --dry-run --allow-dirty=false`.
4. Add `cargo publish` step to `.github/workflows/release.yml`, gated on `CARGO_REGISTRY_TOKEN` secret. Runs only on tag push.
5. README install section: add `cargo install clipboard-history-mcp` as the recommended path for Claude Code / CLI users, above the existing "From source" section.
6. Test the published crate end-to-end on a clean machine: `cargo install ... && clipboard-history-mcp install && claude mcp add ...`.

**Risks.**

- `clipboard-history-mcp` name on crates.io may already be taken — check before scope-locking. If taken, fall back to `clipboard-history` or `mcp-clipboard-history`.
- crates.io requires the binary to build with stable Rust — verify against `rust-toolchain.toml` if pinned to a nightly feature.

**Effort.** ½ day, contingent on name availability and crates.io review response.

**Success.** `cargo install clipboard-history-mcp` on a clean macOS machine produces a working binary that registers correctly.

### T5 — MCP Registry submission

**Scope.** Per the 2026-05-08 marketplace research: there is no curated Anthropic marketplace; there is the **MCP Registry** (`registry.modelcontextprotocol.io`) backed by Anthropic + GitHub + PulseMCP + Microsoft. Submission is a CLI push, no human review.

**Concrete steps.**

1. **`server.json`** at repo root with:
   - `$schema: https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json`
   - `name: io.github.d-khomenko/clipboard-history-mcp`
   - `version: 0.6.0-alpha.0` (or whatever ships)
   - One package entry: `registryType: "mcpb"`, `identifier: <full GitHub release URL of .mcpb>`, `fileSha256: <hash>`, `transport.type: "stdio"`.
   - `environmentVariables` declared so clients can render config UI: `CLIPBOARD_VAULT_PATH`, `CLIPBOARD_HISTORY_MAX`, `CLIPBOARD_NEVER_STORE_SECRETS`, etc.
   - Optional `_meta.io.modelcontextprotocol.registry/publisher-provided` for categories + screenshots.
2. **sha256 in CI**: extend `.github/workflows/release.yml` to compute `openssl dgst -sha256 clipboard-history-mcp.mcpb` and write into `server.json` before publish.
3. **`mcp-publisher` GitHub Action** added to `release.yml` running on tag push: `mcp-publisher login github && mcp-publisher publish`. Uses GitHub OIDC, no token to manage.
4. **`SECURITY.md`** at repo root: how to report vulnerabilities (private email or GitHub Security advisory), supported versions, known threat-model boundaries (master-key-v1 raw-key compat note).
5. **Verify `.mcpb` notarization**: audit existing `release.yml` for macOS signing+notarization steps. If absent, decide whether to add (1-3 hrs) or document the limitation in SECURITY.md and downstream Claude Desktop install UX.

**Effort.** ½ day for items 1-4; +1-3 hrs if notarization gap exists.

**Success.** `curl "https://registry.modelcontextprotocol.io/v0.1/servers?search=clipboard-history-mcp"` returns the server. New tag → new version published automatically.

## 4. Sequencing

```
T1 (1 day) ──┬─→ T2 (1 wk) ─┐
             ├─→ T3 (½ d)   ├─→ release v0.6.0 ─→ T6 (outreach)
             ├─→ T4 (½ d) ──┤
             └─→ T5 (½ d) ──┘
                  ↑
                  T5 depends on T4-era release.yml polish
```

- **T1 first.** Quality polish before anyone reads the code from a registry listing or HN post. Cheap to ship.
- **T2 + T3 + T4 in parallel** after T1 lands. T2 is the long pole. T3 and T4 are fillers for T2's gaps.
- **T5 right before release.** Depends on T4 ergonomically — both touch `release.yml` — and the sha256 step needs the actual `.mcpb` artefact to hash.
- **T6 last.** Don't broadcast until the registry listing is live and v0.6.0 is tagged.

Each track ships as one or more PRs against `main`. v0.6.0 tag goes after T1-T5 merge.

## 5. Out of scope (deferred to v0.7+)

| Item | Why deferred | Target |
|---|---|---|
| Windows port | Service-installer scaffolding work is non-trivial; need market signal from v0.6 macOS+Linux uptake before tripling effort | v0.7 |
| Persistent unlock-secret audit log + `get_unlock_log` tool | Strong differentiator but not blocking adoption; current `tracing` log is sufficient for personal-use | v0.7 |
| Time-boxed secret TTL | Same: nice-to-have security feature, not table-stakes | v0.7 |
| Auto-redaction of secret previews returned via MCP | Already partly done (`text: null` for secret rows); polish in v0.7 | v0.7 |
| Fuzzy / typo-tolerant search | FTS5 BM25 is "good enough" for v0.6; adding fzf-style match adds dep | v0.7 or skip |
| Semantic / vector search (LanceDB / sqlite-vec) | High infra cost, low immediate value when FTS works | v0.8 if user signal |
| LLM-aware tools (`summarize_clip`, `extract_entities`, `jwt_decode`) | Genuinely unique direction but premature without v0.6 user feedback | v0.7 |
| Reverse Obsidian sync (search vault → restore to clipboard) | Inverts the abstraction; needs separate design pass | v0.7 |
| Cross-device sync | Largest stickiness driver in native managers but needs server infra (or P2P + CRDT design); no clear MVP path | indefinite |
| Snippets / templates / paste-stack | Differentiates from MCPs but user already has alternatives (Alfred, Raycast); low ROI for a clipboard history MCP specifically | maybe never |
| Drag-drop GUI / menubar status item | Out of scope for an MCP — Maccy and friends own that UX | maybe never |
| Per-app exclude rules beyond name list | Marginal value for the engineering | v0.7 if requested |
| FTS5 index NULL-text-secret robustness | Audit found the test gap; if a real bug surfaces, hot-fix; otherwise v0.7 | v0.7 |
| Schema migration framework | Currently ad-hoc. Worth doing when next schema change lands; T2 is the natural trigger but the migration code itself is out of T2's scope to keep T2 focused | v0.7 |

## 6. Success criteria for v0.6

The release ships when **all** are true:

1. `cargo install clipboard-history-mcp` works end-to-end on a clean machine.
2. The server is discoverable in the MCP Registry (`registry.modelcontextprotocol.io`).
3. PNG and FileURL pasteboards are captured and round-trip via `restore_clip`.
4. Pinned items survive a 1000+ capture HISTORY_MAX prune cycle.
5. No `.expect()` / `.unwrap()` reachable from production paths (verified via grep + manual review).
6. `is_transient()` returns `true` for 1Password / Bitwarden pasteboard reads.
7. `awesome-mcp-servers` PR open or merged.
8. CHANGELOG entry covers all six tracks with concrete user-facing language.

## 7. Decomposition into per-track sub-specs

This roadmap is one document. Each track gets its own sub-spec under `docs/superpowers/specs/2026-05-NN-v0.6-T<n>-<topic>-design.md` written immediately before the track enters `writing-plans`. The sub-spec format:

- §1 — what this track adds, scoped narrowly.
- §2 — reference to this roadmap.
- §3 — concrete file-by-file changes, with diffs of schema / API / CLI / README.
- §4 — tests added.
- §5 — explicitly *not* in this track (so reviewers don't ask).
- §6 — definition of done (matches §6 of this roadmap for the relevant bullet).

The order in which sub-specs are written follows §4 sequencing. T1 first, then T2/T3/T4 can parallel, T5 close to release, T6 trivial-no-spec.

## 8. Open questions

- **`pin_item` MCP tool wiring** (T3): does it actually exist and is the prune logic pin-aware? Need to grep `src/mcp/tools.rs` and `src/core/store.rs` before T3 sub-spec.
- **macOS notarization** (T5): does `release.yml` notarize the binary inside the `.mcpb`? If not, decide between adding it now or documenting the gap.
- **Crate name on crates.io** (T4): is `clipboard-history-mcp` available? If not, what fallback name is acceptable?
- **`CLIPBOARD_MAX_BLOB_BYTES` default** (T2): 10 MB is a guess. Real-world copy sizes for screenshots range 100 KB–5 MB; design videos/PDFs can hit 50+ MB. Pick a value that doesn't silently drop common copies.
- **Vault image rendering in Obsidian** (T2): confirm Obsidian renders relative-path PNG references inside frontmatter-bearing markdown without manual config.

These are resolved during each track's sub-spec phase, not now.
